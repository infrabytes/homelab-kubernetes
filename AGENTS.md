# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project overview

GitOps-driven homelab Kubernetes cluster. A Talos Linux cluster runs on Proxmox VE; it is provisioned with Terragrunt + OpenTofu (`infra/`) and applications are delivered by ArgoCD from this same repo (`platform/` + `apps/`).

Stack: Talos Linux - Kubernetes - Cilium (kube-proxy-free, L2 LB, Gateway API, WireGuard encryption, Hubble) - ArgoCD - cert-manager (Let's Encrypt DNS-01) - external-dns - VictoriaMetrics + Loki + Grafana (self-hosted observability) - SOPS/age - Renovate.

## Commands

```sh
pre-commit run --all-files         # run every lint/format gate locally
cd infra && terragrunt validate --all
cd infra && terragrunt plan --all
cd infra && terragrunt apply --all   # CAUTION: mutates the live cluster
cd infra && terragrunt destroy --all # CAUTION: destroys everything
# Infra changes are normally applied by Atlantis from PRs (automerge on):
# atlantis.yaml at the repo root defines the projects/workflow; the server is a
# Helm release in the single-node k3s cluster on the windrunner VM
# (platform/atlantis/, registered in ArgoCD as cluster `windrunner`, behind SWAG
# at atlantis.icaninto.space). Only its credentials (the atlantis-env Secret) and
# the cluster install (ansible/windrunner-k3s.yml) live outside that manifest.
# Apply consumes the plan written by plan (-out $PLANFILE), so a failed or
# stale plan blocks apply: comment `atlantis plan` again before `atlantis apply`.
# Atlantis plans and applies the *branch*, so a branch that predates another
# merge to the same unit re-applies the old values and silently reverts it —
# hence `execution_order_group`, and hence: rebase/re-plan a PR after anything
# else in its unit merged (a stale apply of #228 reverted #227's argo-cd sizing).
# Plans and applies are ordered by each project's `execution_order_group`
# (mirroring the Terragrunt DAG: cluster -> viewer-kubeconfig/addons ->
# argocd-config), with abort_on_execution_order_fail; a new unit needs a group.
# Never add `depends_on`: with groups it blocks the first global apply
# (runatlantis/atlantis#5791).
# Every project pins `terraform_distribution: opentofu` + `terraform_version`:
# without a distribution Atlantis looks for Terraform, re-resolves the newest
# release its `required_version` allows on every plan, and fails when its
# downloader rejects HashiCorp's content type.
# Terragrunt, sops and kubectl come from the chart's initConfig in
# platform/atlantis/application.yaml, so their pins must match tg_version in the
# CI workflows and the windrunner setup script.
sops infra/secrets.sops.yaml         # edit secrets (re-encrypts on save)
# k3s management cluster + Atlantis/SeaweedFS bootstrap (idempotent; also refreshes the
# atlantis-env and seaweedfs-s3-config Secrets):
sops exec-env infra/secrets.sops.yaml \
  'ansible-playbook -i ansible/inventory.json ansible/windrunner-k3s.yml --check --diff'
# PVE host maintenance (dry run; canary = add --limit proxmox02, needs explicit go-ahead):
sops exec-env infra/secrets.sops.yaml \
  'ansible-playbook -i ansible/inventory.json ansible/proxmox-node-updates.yml --check --diff'
```

Agent environment: OMP sessions run directly on the host (no sandbox). Tools and the SOPS age key are the host's; if a tool is missing from PATH, ask the user.

## Validation & pre-commit

Every change must pass `.pre-commit-config.yaml`; CI runs it on push/PR on the self-hosted `homelab-runner` (`.github/workflows/pre-commit.yaml`, pinned tool versions, tools served from the pod-local cache hydrated from the shared seed volume; see `README.md`). PR runs are diff-scoped (`--from-ref`/`--to-ref`); pushes to `main` and PRs touching hook config run the full `--all-files` sweep. Jobs run fully concurrent (per-pod emptyDir caches; only the warm workflow writes the seed, atomically — it wipes the pod-local trees before rebuilding, so the seed never accumulates old versions). Notable hooks:

- `terragrunt_fmt` + `terraform_tflint` (config: `infra/cluster/.tflint.hcl`) for `infra/`
- local `terragrunt-validate` hook (`.github/scripts/terragrunt-validate.sh`): `terragrunt validate --all` on `infra/`; skips without the SOPS age key (e.g. CI), enforcing locally where secrets decrypt
- `yamllint` (`.yamllint.yaml`; ignores `secrets.sops.yaml`, 160-char lines)
- `kubeconform` on `platform/`, `apps/` and `argocd/` YAML
- `ansible-lint` on `ansible/` (config: `ansible/.ansible-lint`)
- no chart-render hook: the render gate is the PR preview (`preview` required check, Argo CD's own renderer). Duplicate mapping keys are `yamllint`'s `key-duplicates`; the rule cannot see inside a `helm.values` block scalar, which is the one gap left (converting values to Argo CD's `valuesObject` would close it). No hook checks resource declarations either: review applies the sizing convention, and the memory-rightsize sandbox proposes corrections from measured usage
- local `tenant-config-check` hook (`.github/scripts/check-tenants.py`): the tenant list (`argocd/tenants/tenants.json`, members with an explicit tailnet `identity` and optional GitHub `user`) and the openbao postStart `TENANTS` marker (`<tenant>:<namespace>[:<login>[|<login>]]`) must agree on tenant/namespace/logins; members are validated (identity charset, duplicate identities, `@github` identities matching their login); also `sh -n`s the postStart script and renders `charts/tenant-access` per tenant, asserting the RoleBinding/ClusterRoleBinding/ServiceAccount/SecretStore and that both bindings' subjects equal the member identities (skips helm/PyYAML when missing)
- `detect-secrets` (baseline: `.secrets.baseline`); never add plaintext secrets. The baseline carries **no result entries** — known false positives are filtered instead: `infra/secrets.sops.yaml` and `.sops.yaml` are excluded by file (encryption is enforced by the `sops-encrypted` hook), and lines containing `passwordKey:`/`secretKeyRef`/`argocdServerAdminPassword` (chart key names, not credentials) are excluded by line. Keep it that way: drift-prone result entries get auto-rewritten by the hook on every partial commit. New false positive → extend the `--exclude-lines`/`--exclude-files` regexes in the baseline's `filters_used` (regenerate via `detect-secrets scan --exclude-files '<regex>' --exclude-lines '<regex>'`). `apiKeySecret:`/`tokenSecret:` are excluded for the same reason: a `helm.values` block scalar reaches the detector as one string, so the `apiKeySecret:` keyword fires on the whole block and `grafana-mcp` was previously passing only because a `secretKeyRef:` line happened to sit in it.
- `renovate-config-validator` for `renovate.json`
- `ruff-check` (astral-sh/ruff-pre-commit) for Python files
- local `sops-encrypted` hook; `*.sops.yaml` files must be encrypted

## Renovate

`renovate.json` is the single source of truth for dependency scanning. Coverage today:

- `infra/env.hcl` version pins → regex custom managers (`talos_version`, `kubernetes_version`, `cilium_chart_version`, `gateway_api_crds_version`). **Every version field in `env.hcl` MUST have a matching `customManagers` entry.**
- Terraform `helm_release` (ArgoCD in `infra/addons/main.tf`) → `terraform` manager (helm datasource). The `grafana/grafana` provider pin in `infra/grafana-cloud-config/versions.tf` is also auto-discovered by the `terraform` manager — no `customManagers` entry needed for provider pins in `.tf` files.
- `.github/workflows/renovate.yaml` `RENOVATE_VERSION` (the self-hosted Renovate image) → regex custom manager (`docker` datasource on ghcr.io/renovatebot/renovate), grouped with the `renovatebot/pre-commit-hooks` rev by a `renovate` package rule: same release stream, never bump one alone. This workflow *is* Renovate: `ubuntu-latest`, a GitHub App installation token (repo variable `RENOVATE_CLIENT_ID`, secret `RENOVATE_APP_PRIVATE_KEY`), triggered by `0 5 * * *`, `workflow_dispatch`, `workflow_run` completions on `renovate/*` branches, and dashboard/PR `edited` events whose job-level `if` ignores both bots' own edits (an App token's writes fire workflow events, so an unguarded edit trigger would loop). The `workflow_run` path must stay outside that actor guard: it is what merges a branch the previous run left waiting on CI, and the bot's own push is what triggers it. This group sets `minimumReleaseAge: null` because only the pre-commit hook reports a release timestamp, so the 3-day gate would split the pair. `prHourlyLimit: 0` in `renovate.json` exists for the daily schedule; do not re-add the default 2. `prConcurrentLimit` is 20, not the default 10: minor/major PRs are now held for a human, and ten parked bumps would block creation of the patch PRs that merge themselves. The image pin and the pre-commit hook rev are the same release stream, so one branch must move both.
- ArgoCD `Application`/`ApplicationSet` manifests under `platform/`, `apps/` and `argocd/` (cert-manager, external-dns, spegel, the ARC charts, the committed `platform` Application and the `apps`/`tenants` ApplicationSets) → `argocd` manager (helm datasource; OCI charts like cert-manager and spegel resolve via the `docker` datasource on quay.io/ghcr.io; a git-sourced chart like agent-sandbox resolves its `targetRevision` via the `git-tags` datasource, then gets overridden to a timestamped one — see the agent-sandbox bullet). The `tenants` ApplicationSet references an in-repo chart by `path`, and in-repo charts (`charts/*`) carry no upstream version — neither needs a manager.
- Agent Sandbox's controller image tag → regex custom manager scoped to `platform/agent-sandbox/application.yaml` (`docker` datasource on `registry.k8s.io`). The image tag must track the chart tag, so both pins are grouped into one `platform` branch by the `matchFileNames: platform/**` package rule; never bump just one. Both pins are then overridden to `github-releases` on `kubernetes-sigs/agent-sandbox` by one `matchFileNames: platform/agent-sandbox/application.yaml` package rule (`overrideDatasource`/`overridePackageName`/`overrideDepName`): the extracted `targetRevision` (git-sourced chart, `git-tags`) and `image.tag` (`docker` on registry.k8s.io) carry no release timestamp, so `timestamp-optional` exempted them from the 3-day gate, and `git-tags` offers tags upstream has not released yet (v1.0.8 was tagged 2026-10-22, released later). `github-releases` only lists published releases and supplies `published_at`; the release job promotes the tag's images before publishing, so `image.tag` still names a real image — never give either pin back a timestamp-less datasource.
- The alert sandboxes pin two binaries: `@earendil-works/pi-coding-agent` in `platform/alert-triage/agent-config.yaml`, `platform/alert-triage/memory-rightsize-agent-config.yaml` and `platform/alert-triage/breaking-change-agent-config.yaml` (regex custom manager, `npm` datasource — the agents' model catalogs and CLI flags follow this version), and `KUBECTL_VERSION` in `platform/alert-triage/sandbox-template.yaml` and `memory-rightsize-sandbox-template.yaml` (regex custom manager, `github-tags`, `value: vX.Y.Z`). Each pin appears once per sandbox and all three sandboxes must stay on the same pi version, so one manager covers the three files. The kubectl pin must match `kubernetes_version` in `env.hcl`, same rule as the `Azure/setup-kubectl` pin in the PR-preview and gate workflows (one manager covers both workflows and the two sandboxes).
- Review policy is Renovate's own: `automerge: false` for `minor`+`major` plus `addLabels: [needs-review]` (after the age rule, because a later `packageRule` wins over its `automerge: true`). That label is the analysis trigger: `.github/workflows/breaking-change-analysis.yaml` runs on `pull_request: labeled` filtered to `needs-review` + a `renovate/` branch, starts the sandbox in `platform/alert-triage/`, and posts its verdict as a PR comment with `GITHUB_TOKEN` — the sandbox has no GitHub token and no cluster identity (the `arc-runner` SA can only create/read claims and pod logs in `alert-triage`). `continue-on-error` is deliberate: `renovate.yaml` merges on the `workflow_run` conclusion, and a model failure must not stall the merge path. `renovate-atlantis-apply.py` refuses to auto-apply a `needs-review` PR, so a held infra bump waits for one human `atlantis apply` comment (which Atlantis then automerges).
- The hubble-observer chart is pinned twice: the chart Application's `targetRevision` (OCI chart, `docker` datasource) and the `oci.reference` of its dashboard CR in `platform/observability/dashboards/flows-dashboard.yaml` (regex custom manager, `docker` datasource on ghcr.io) — the dashboard JSON is pulled from the chart artifact, so both pins are the same version; the `platform/**` rule groups them into one branch. Never bump just one.
- The Grafana GitHub data source (`platform/observability/grafana-github-datasource.yaml`) pins the `grafana-github-datasource` plugin it needs; the operator's plugin reconciliation installs exactly that version via `GF_INSTALL_PLUGINS`, and its `github-releases` custom manager tracks `grafana/github-datasource` tags (which equal the plugin versions). The runner dashboard's per-run links break if the plugin is bumped without the dashboard JSON's `queryType`/`options` shape.
- The Cilium chart is pinned twice: `cilium_chart_version` in `infra/env.hcl` (cluster release) and the `hubble-ui` app's `targetRevision`. The standalone Hubble UI must match the deployed chart, so the `matchDatasources: helm` + `matchPackageNames: cilium` rule groups both into one `cilium chart` branch; never bump just one.
- Renovate only fetches release notes when a dependency has a `sourceUrl` (the datasource does not matter: the changelog lookup reads `sourceUrl` + versions), so a chart whose index or OCI artifact carries no source gets none and the gate has nothing to read. `csi-driver-nfs` and the spegel OCI chart are pinned with an explicit `packageRules.sourceUrl`, each verified against the upstream tag scheme. Do not add one for `ghcr.io/onzack/helm-charts/hubble-observer` (no releases upstream) or tailscale (its release body is a link to tailscale.com/changelog); those stay unverifiable and the analysis agent covers them.
- Raw manifests (`metrics-server`, `kubelet-serving-cert-approver`) → `kubernetes` manager (image + API versions). It regexes raw `image:` lines rather than parsed pod specs, which is why the ARC runner image inside `application-scale-set.yaml`'s `helm.values` block scalar is tracked too: keep that pin inline (`image: repo:tag`), because an `image:` + nested `tag:` shape silently drops it (hence the agent-sandbox custom manager).
- `ansible/requirements.yml` collection pins → the built-in `ansible-galaxy` manager (`galaxy-collection` datasource on galaxy.ansible.com); no custom manager needed — the `galaxy` (roles) datasource cannot resolve collections and fails lookup.
- `.github/workflows/pre-commit.yaml` + `.github/workflows/warm-tool-cache.yaml` CLI pins (terragrunt `tg_version`, tofu `tofu_version`, tflint `tflint_version`; kubeconform + pyyaml stay pre-commit-only) → regex custom managers whose `managerFilePatterns` cover both files; `.pre-commit-config.yaml` → `pre-commit` manager. The `actions/setup-python` `python-version` pin needs NO custom manager: the built-in `github-actions` manager already tracks it in every workflow file — don't add one.
- `atlantis.yaml`: the per-project `terraform_version` (OpenTofu, matching the atlantis-homelab image) is tracked by the same regex custom manager as the workflows' `tofu_version`; never bump it alone.
- `platform/atlantis/application.yaml`: the `initConfig` script pins terragrunt, sops and kubectl as download URLs → regex custom managers (`github-tags` for terragrunt/kubectl, `github-releases` for sops) that read the version out of the URL; `matchDepNames` package rules group each pin with its siblings in the CI workflows and `ansible/windrunner-setup.sh`, because those versions must agree.
- `ansible/windrunner-k3s.yml`: `k3s_version` → regex custom manager (`github-releases` on `k3s-io/k3s`), grouped with the Kubernetes pins. A `+k3sN` rebuild of the same Kubernetes version needs a manual edit: semver ignores build metadata, so Renovate never sees it.
- `.github/workflows/breaking-change-analysis.yaml` + `.github/workflows/warm-tool-cache.yaml`: kubectl pin (`Azure/setup-kubectl`, must match `kubernetes_version` in `env.hcl`) → regex custom manager; the `helm/helm` CLI pin (`Azure/setup-helm`) covers `.github/workflows/pre-commit.yaml` + `warm-tool-cache.yaml`. Neither action runs in `pr-preview.yaml` any more: `argocd-diff-preview` embeds Helm and needs no `kubectl`. The Argo CD chart it installs into the ephemeral cluster is pinned by `ARGOCD_CHART_VERSION` in `pr-preview.yaml` (helm datasource, `argoproj.github.io/argo-helm`) and must match the `argo-cd` chart pin in `infra/addons`, so the preview renders with production's Argo CD.
- Runner CLI pins (the CLIs without setup actions that the `pr-preview` workflow runs on the self-hosted runner: argocd-diff-preview, gh, kind) → regex custom managers matching the job-env `*_VERSION` values in `.github/workflows/pr-preview.yaml` (github-releases datasource). Installed per-run by the workflow from those pins, so a bump is one env value; unlike the setup actions' tools they do not live in the pod-local `RUNNER_TOOL_CACHE` (`/opt/tool-cache/local/runner`, hydrated from the shared seed volume; see `README.md`). The `docker:dind` sidecar the preview's kind cluster needs is chart-generated (`containerMode: dind`, `platform/arc`); its image is not tracked here and Renovate cannot bump it.
- The `minimumReleaseAge: 3 days` rule carries `minimumReleaseAgeBehaviour: timestamp-optional`. Renovate reports a release timestamp only for Docker Hub images (the docker datasource note reads "Only supported on Docker Hub") and never for `git-tags`, so under the default `timestamp-required` plus `internalChecksFilter: strict` any branch containing such an upgrade — e.g. the `platform` group with the ARC runner image or the ghcr.io OCI charts — is never created and sits in "Pending Status Checks" on the dependency dashboard indefinitely (a grouped branch waits for its *newest* member, so one timestamp-less upgrade blocks every helm/tag bump beside it). Every rule that sets `minimumReleaseAge` must carry the behaviour, otherwise the 3-day gate becomes a permanent block; when adding a datasource, check its `releaseTimestampSupport`. The flip side: `timestamp-optional` treats a timestamp-less release as stable, so those deps are **never** age-gated — `github-tags` (commit date) and `github-releases` (`published_at`) do carry timestamps and are gated, `git-tags` and non-Docker-Hub `docker` are not. A pin that must honour the gate therefore needs a timestamped datasource, not a longer `minimumReleaseAge` (agent-sandbox's `github-releases` override above is the worked example).

**PR preview** (`.github/workflows/pr-preview.yaml`): a self-hosted ARC runner (`homelab-runner`) renders the base vs. target diff in an **ephemeral kind cluster inside the runner pod** — `argocd-diff-preview`'s approach 1 of the [self-hosted-runner guide](https://dag-andersen.github.io/argocd-diff-preview/getting-started/self-hosted-gh-runner/) — and posts one comment with `output/diff.md`. The tool creates the cluster in the pod's docker daemon (ARC `containerMode: dind`, i.e. the chart's privileged `docker:dind` sidecar, which is why `arc-runners` carries the PSA `privileged` exemption in `infra/addons`), installs Argo CD `ARGOCD_CHART_VERSION` into it, renders, then deletes it; subnets come from `.github/kind-config.yaml` because kind's defaults overlap the host's pod/service CIDRs. The repo and every chart it renders are public, so the run needs **no credentials and no host-cluster access**: the `arc-runner` SA holds no RBAC (`platform/arc/service-account.yaml`; the breaking-change claim grant lives in `platform/alert-triage/rbac.yaml`). The workflow itself runs on every PR (it is a required check, and a paths-filtered one would leave PRs pending forever); a `tj-actions/changed-files` gate skips the expensive steps for PRs touching no `platform/`/`apps/`/`argocd/`/`charts/` manifest. The diff is the entire PR gate — no preview deployment, no health checks (the former vCluster deploy/health stage with its per-app allowlist, chart mirroring, CRD supply, secret copy and cleanup job was retired; runtime issues surface post-merge via the ArgoCD sync + Grafana, rollback is a git revert). The runner PAT lives in the `arc-runner-auth` Secret (namespace `arc-runners`), synced by ESO from OpenBao (`secret/arc-runner-auth`); the addons unit only creates the namespace.

**Runtime validation** — none in the PR gate: chart apps and raw manifests are covered by the diff render (`preview`, a required check) plus pre-commit (kubeconform validates raw repo manifests). Nothing rejects a pod without requests/limits at admission, so a missed `resources` block lands at BestEffort QoS until review or the memory-rightsize agent fixes it. Deploy-time behavior (crashloops, bad images, webhook rejections) is observed after merge: ArgoCD syncs `main` automatically, Grafana monitors the result, rollback is a git revert.

When adding or removing a component:

- New version pin in `env.hcl` (or any new `*.hcl`/workflow file) → add the corresponding custom manager; on removal, delete the entry.
- New manifests under `platform/`, `apps/` or `argocd/` → auto-discovered by the `argocd`/`kubernetes` managers, no config change needed (just ship the manifest).
- Removing an Application/manifest → no config change needed; remove the manifest only.

Verify renovate changes with `pre-commit run renovate-config-validator --all-files` (pinned renovate version) and watch the next self-hosted run's Dependency Dashboard for extraction errors.

- Custom-manager file matching is `managerFilePatterns` in Renovate 44.x (was `fileMatch` before v44). Always validate with the pinned version (`pre-commit run renovate-config-validator --all-files`); a stale `npx` cache runs an old renovate and reports false errors.
- Local dry-runs need Node matching renovate's engine (44.x: `^24.11.0`; use the pre-commit `node_env-lts` node if the system node is too new) and a token via `RENOVATE_HOST_RULES` (`platform=local` does not auto-inject `RENOVATE_TOKEN`).

## Conventions

- **Terragrunt**: put unit inputs (and derived values) in `infra/env.hcl`, one `locals.cluster` / `locals.viewer_kubeconfig` / `locals.addons` / `locals.grafana_cloud` / `locals.argocd_config` map. A unit's `terragrunt.hcl` only wires `inputs = local.env.locals.<unit>` and carries no values. `apply --all` runs `cluster` first, then `viewer-kubeconfig` and `addons` (independent siblings), then `argocd-config`; `destroy --all` reverses it. Providers resolve the cluster connection from `cluster/artifacts/kubeconfig` via `env.hcl`, so no `KUBECONFIG` export is needed. The node list exists once, in `ansible/inventory.json` (Ansible's native JSON inventory, read with `-i`): `env.hcl` derives `locals.nodes` from its `pve` host vars (`talos_role`/`talos_node`/`pve_node`/`pve_vmid` plus the VM attributes), so a node change is one file edit and there is no drift to check. The credential files (`kubeconfig`, `talosconfig`, `viewer-kubeconfig`) live in the machine-invariant `credentials_dir` (`/var/tmp/homelab-artifacts` — state stores each resource's absolute filename, so a checkout path would plan creates in every other workspace) with symlinks in `cluster/artifacts/`; they sync with the state bucket's `artifacts/` prefix via `before_hook`/`after_hook` in `root.hcl` running `scripts/sync-artifacts.sh` (download before plan/apply, upload after apply — a missing bucket object is a cache miss: plan shows create, apply regenerates and re-uploads; hook output is silent, contents never appear in Atlantis output). The cilium/gateway-api inline manifests stay local-only in `cluster/artifacts/` (accepted plan noise when absent). The `grafana-cloud-config` unit is the exception: Grafana Cloud API via the grafana/grafana provider (stack service-account token from SOPS), no `dependencies {}` block, runs in parallel.
- **Secrets**: one SOPS-encrypted file, `infra/secrets.sops.yaml` (recipients in `.sops.yaml`). Edit only via `sops`. The age key is NOT in the repo.
- **ArgoCD**: `platform/` = cluster-scoped/admin resources; `apps/` = regular applications. The `platform` Application and the `apps`/`pdeu`/`tenants` ApplicationSets are committed under `argocd/appsets/` and applied by the Terraform-managed bootstrap ApplicationSet (`infra/argocd-config/`): one intermediate Application per appset dir, name `appset-{{path.basename}}`. They sync from `main` with `automated` sync (prune + selfHeal), so pushing to `main` deploys. `platform` is an app-of-apps: `directory.include: "*/application*.yaml"` makes it apply only the per-component Application manifests, and each component Application owns its chart release plus the manifests in its folder. Server-side apply is set by the apps whose objects exceed the 256KB-capped `last-applied-configuration` annotation: the CRDs of `prometheus-operator-crds`, `cloudnative-pg`, the two ARC charts and `grafana-operator`, plus `observability` for the 468 KB vendored Node Exporter Full ConfigMap. Adding `apps/<name>/` needs no registration. A platform component is one folder with one `application.yaml` carrying both sources: the Helm chart (inline `values`, untouched by the split) and the folder itself as `path: platform/<component>` with `directory.exclude: "application*.yaml"`, so the release and its companion manifests (DB, RBAC, ESO objects, routes, netpols) sync, heal and roll back as one app (`platform/cert-manager/application.yaml` → Application `cert-manager`). Those committed component Applications carry no `resources-finalizer.argocd.argoproj.io`, so deleting a folder prunes the Application and leaves the release's objects running: removing a component means deleting its resources by hand afterwards (the Kyverno uninstall, #533, had to). Every Application manifest under `platform/` must be named `application*.yaml`: folder sources exclude that glob, and a sibling named otherwise would be applied by two Applications (the PR preview's diff makes the double ownership visible). One Application has one destination namespace, so a folder hosting several components in separate namespaces keeps one app per component and splits the manifests across them: `arc` (`gha-runner-scale-set-controller`, `gha-runner-scale-set` + the runner manifests), `observability` (`grafana-operator`, `loki`, `victoria-metrics` + `observability` for the Grafana CRs, dashboards, alerting and the PG cluster). Adding a new ApplicationSet = add a dir under `argocd/appsets/` (no Terraform change). Two apps target the k3s management cluster by name instead of the Talos cluster: `platform/atlantis/` and `platform/seaweedfs/` (`destination.name: windrunner`, `CreateNamespace=true`). Neither folder holds companion manifests, because a namespace or Secret next to them would be created in the Talos cluster instead: registering that cluster and staging `atlantis-env` / `seaweedfs-s3-config` is `ansible/windrunner-k3s.yml`'s job, and there is no GitOps path for those Secrets because they are credentials. Tenant access is data-driven: `argocd/tenants/tenants.json` feeds both the committed `tenants` ApplicationSet (one `charts/tenant-access` render per tenant: RBAC, ESO ServiceAccount, namespaced OpenBao store) and the openbao postStart `TENANTS` marker (mount, policies, k8s/OIDC roles); the `tenant-config-check` hook fails when the two drift. The local Grafana stack is GitOps: `platform/observability/` carries the `Grafana`/`GrafanaAlertRuleGroup`/`GrafanaContactPoint`/`GrafanaNotificationPolicy`/`GrafanaFolder` CRs plus the CloudNativePG `Cluster` that backs Grafana's database, the datasource-provisioning ConfigMap mounted into the Grafana pod (VM-to-Loki correlations — the `GrafanaDatasource` CRD cannot express them), and `platform/observability/dashboards/` the `GrafanaDashboard` CRs — chart-shipped ones (imported from chart ConfigMaps or the OCI artifact) plus the in-repo ConfigMaps (Network Policies, GitHub Actions runners, the vendored grafana.com 1860 "Node Exporter Full"). The GitHub Actions dashboard is the only one backed by a non-metrics source: `grafana-github-datasource.yaml` provisions the GitHub API data source (read-only PAT from `infra/secrets.sops.yaml` via the `grafana-github-token` Secret) and declares its plugin, because ARC metrics expose no run id to link from. No Terragrunt unit talks to the local Grafana; `grafana-cloud-config` keeps only the Cloud watchdog (Talos folder, maintenance dashboard, maintenance + heartbeat rules).
- **Storage homes**: NAS (`192.168.0.22:/nas`) via the `nfs-nas` StorageClass from the `csi-driver-nfs` chart backs the observability TSDBs (VictoriaMetrics, Loki); Longhorn keeps cluster state (Grafana's CloudNativePG cluster, ARC tool cache) and its `storageReserved` is never lowered to fit a TSDB. `nfs-nas` uses `reclaimPolicy: Retain` (a PVC prune must not delete 90 days of data) and `mountPermissions: "0777"` (the driver creates the volume subdir as a squashed user; Loki writes as uid 10001). SeaweedFS's volume data sits on a windrunner `local-path` PVC (`seaweedfs-all-in-one-data`, 100 Gi, no expansion) rather than either: it is the S3 store Velero writes to.
- **Observability split**: cluster metrics/logs go only to the in-cluster VictoriaMetrics/Loki (namespace `observability`, both on `nfs-nas`); Alloy writes to those two endpoints; its only `metricsTuning` trims are the kube-state-metrics NetworkPolicy include and the host-metrics allowlist union behind the Talos node dashboard. Grafana Cloud is the out-of-cluster watchdog: it holds the PVE-maintenance rules, the `cluster-heartbeat` dead-man rule (fed by `platform/observability/heartbeat-cronjob.yaml` pushing into Cloud Loki) and Discord as the notification transport (hand-configured `GrafanaBot` contact point + its policy); it gets no cluster metrics/logs. Adaptive Metrics was retired with the free tier, so no `grafana-adaptive-metrics` provider is in play.
- **Versions**: dependency pins live in `infra/env.hcl` (`talos_version`, `kubernetes_version`, `cilium_chart_version`, `gateway_api_crds_version`), `infra/*/versions.tf` (provider pins), `.github/workflows/pre-commit.yaml` + `.github/workflows/warm-tool-cache.yaml` (CLI tools), `.pre-commit-config.yaml`, `ansible/requirements.yml` (collection pins), `ansible/windrunner-k3s.yml` (k3s), `platform/atlantis/application.yaml` (terragrunt/sops/kubectl for the Atlantis initConfig), ArgoCD `Application` chart `targetRevision`s, and the PR preview job env in `.github/workflows/pr-preview.yaml` (the Argo CD chart version, argocd-diff-preview, gh, kind). Renovate drives bumps, so don't bump versions manually without a reason. When adding/removing a pinned dependency, update `renovate.json` per the [Renovate section](#renovate).
- **Resource sizing**: derive requests/limits from the longest retained Grafana window — memory request = p95 rounded up to 64Mi (32Mi floor), memory limit = max(1.5x request, 1.25x observed peak), CPU request = p95 rounded up to 10m, and no CPU limits. State the measurement window in the values comment, and re-derive from the alerting history rather than hand-tuning. Exceptions are one-shot escalations with a recorded re-measure date (the ArgoCD application-controller 3Gi limit escalated on 2026-10-25, after the 2Gi from the day before OOMKilled it during a 44-app fleet sync, is outstanding until 2026-11-08; the ARC runner 2Gi request / 4Gi limit escalated on 2026-10-27 when the runner pods gained the dind sidecar and the in-pod kind cluster, outstanding until 2026-11-10; the application-controller 1Gi/2Gi and applicationset-controller 128Mi/256Mi ones were retired on 2026-10-22), and the remaining observability initial estimates (VictoriaMetrics, Loki, csi-driver-nfs) are dated 2026-09-16 and not yet re-derived.
- **Style**: Conventional Commits — `type(scope): subject`, imperative, lowercase (`conventional-commit` skill); Clean Code principles (`clean-code` skill) — comments terse, why-not-what.
- **Documentation**: keep the root `README.md` (stack overview, bootstrap/day-2 workflows) current — reflect added/removed components, bootstrap-order and exposure changes there. Detailed ops docs stay in `infra/*/README.md`.

## Rules & guardrails

- **Never** push to `main`, force-push, or rewrite history. All changes go through a branch + PR: create a dedicated git worktree under `.worktrees/` (or use the `github` tool's `pr_checkout`), commit there, push the branch, and open a PR to `main` — no direct commits to `main`, no asking first. Auth: gh CLI credential helper (`gh auth git-credential`, HTTPS, no SSH).
- **Never** run `terragrunt apply` / `destroy` / `import` against the live cluster unless the user explicitly asks. These are destructive, real-world operations. Note: opening a PR that touches `infra/` (or `env.hcl`) lets Atlantis auto-apply on the PR and auto-merge — treat pushing a branch + PR as an apply trigger for infra units.
- **Never** commit unencrypted secrets, private keys, or Terraform state. `.terraform/`, `.terragrunt-cache/`, `*.tfstate*`, and `artifacts/` are gitignored, so don't force-add them.
- **Never** edit `infra/secrets.sops.yaml` as plaintext or decrypt it into a committed file. Re-encrypt with `sops -e -i` (CI rejects unencrypted `*.sops.yaml`).
- **Never** delete or regenerate machine secrets (`talos_machine_secrets`); the local state and `artifacts/talosconfig` carry cluster identity. Losing them means the cluster can't be re-adopted.
- Don't touch `artifacts/` outputs (kubeconfig/talosconfig/viewer-kubeconfig); they are generated by the `cluster`/`viewer-kubeconfig` units. `.terragrunt-cache/` is transient, so ignore it.
- Don't modify local tooling (host-side helpers) unless asked.
